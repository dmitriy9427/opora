# 09. Версии и публикация

## SemVer: что обещает номер версии

`МАЖОР.МИНОР.ПАТЧ` — `1.4.2`.

| Часть | Растёт, когда | Пользователь |
| --- | --- | --- |
| патч | исправлен баг | обновляется не глядя |
| минор | добавлено новое, старое работает | обновляется не глядя |
| мажор | что-то сломано: убрано, переименовано, изменено поведение | читает, что поменялось |

`"opora-ui": "^1.4.2"` в чужом `package.json` значит «любая 1.x.x не ниже 1.4.2». Поэтому
ломающее изменение в минорной версии сломает приложения людей **само**, при очередном
`npm install`. Что считается ломающим — таблица в [главе 04](04-api-design.md).

Версии `0.x` — особые: «API ещё не устоялся», ломать можно в минорных. `1.0.0` — обещание
стабильности.

## Changesets: журнал изменений, который пишется по ходу

Плохой способ: перед выпуском вспоминать, что изменилось за месяц. Changesets предлагает
описывать изменение **вместе с ним**.

```bash
npx changeset
```

Инструмент спросит тип (patch / minor / major) и текст — и создаст файл в `.changeset/`:

```md
---
'opora-ui': minor
---

Select: проп `clearable` — кнопка сброса значения.
```

Файл коммитится вместе с кодом. Когда пора выпускать:

```bash
npx changeset version
```

Все накопленные описания удаляются, версия в `package.json` поднимается (по самому
«старшему» типу), а тексты попадают в `CHANGELOG.md`. Остаётся закоммитить и опубликовать.

## Первая публикация в npm — по шагам

Аккаунт создаёте и входите в него **вы** — пароль и код подтверждения не должны проходить
через чужие руки и скрипты.

### 1. Аккаунт

https://www.npmjs.com/signup. Включите двухфакторную защиту (Account → Two-Factor
Authentication) — для публикации пакетов она обязательна.

### 2. Вход

```bash
npm login
```

Откроется браузер. Проверить:

```bash
npm whoami
```

### 3. Имя свободно?

```bash
npm view opora-ui
```

Ошибка `E404` — свободно. Если имя успели занять, поменяйте `name` в `package.json`
(например, на `@ваш-логин/opora` — имена с префиксом аккаунта всегда свободны) и в импортах
в документации.

### 4. Посмотреть, что уйдёт

```bash
npm pack --dry-run
```

Список файлов архива. Должны быть только `dist/`, `package.json`, `README.md`, `LICENSE`,
`CHANGELOG.md`.

### 5. Опубликовать

```bash
npm publish
```

Перед публикацией сам запустится `prepublishOnly` → `npm run check`: линтер, типы, тесты,
сборка, размер, проверка пакета. Что-то красное — публикации не будет.

`"publishConfig": { "access": "public" }` в `package.json` — пакет публичный.

### 6. Проверить

```bash
npm view opora-ui
```

Страница пакета: https://www.npmjs.com/package/opora-ui. В новом проекте:
`npm install opora-ui`.

**Опубликованную версию нельзя изменить.** Ошиблись — выпускайте следующую. Удалить версию
можно только в первые 72 часа (`npm unpublish`), и номер её уже не занять.

## Следующие версии — из GitHub, без токенов

После первой публикации настройте **доверенного издателя** (trusted publishing). npm сам
проверяет, что публикует именно ваш репозиторий и именно этот workflow. Секретов в GitHub
нет — красть нечего.

1. npmjs.com → пакет → Settings → **Trusted Publisher** → GitHub Actions.
2. Organization or user: `dmitriy9427`, Repository: `opora`, Workflow filename: `release.yml`.

Дальше выпуск версии:

```bash
npx changeset version      # поднять версию, обновить CHANGELOG
git commit -am "Версия 0.2.0" && git push
```

и в GitHub: Actions → **«Выпуск в npm»** → Run workflow.

`.github/workflows/release.yml` устанавливает зависимости и вызывает `npm publish --provenance`
(флаг работает только в CI — при ручной публикации с ноутбука его не указывают).
У версии в npm появится отметка **provenance**: из какого коммита и каким workflow она
собрана. Пользователь видит, что пакет собран из открытого кода, а не подменён.

Запуск — вручную, а не на каждый пуш: публикация необратима, и её стоит делать осознанно.

## Демо: Storybook на GitHub Pages

`.github/workflows/ci.yml` при каждом пуше в `main`:

1. `npm run check` — всё, включая проверку упакованного пакета;
2. `npm run build:storybook` — статический сайт;
3. публикация на Pages.

Storybook собирается с относительными путями, поэтому работает в подпапке
`https://<user>.github.io/opora/` без настройки `base`.

На пулл-реквестах выполняются шаги 1–2 без публикации.

## Что ещё бывает у библиотек

| Что | Зачем |
| --- | --- |
| Предварительные версии (`1.0.0-beta.1`, тег `next`) | дать попробовать мажорную версию, не ломая `latest` |
| `npm deprecate` | пометить версию устаревшей с сообщением |
| Визуальные тесты (Chromatic, Playwright screenshots) | поймать изменение внешнего вида |
| Codemod | скрипт, переписывающий код пользователей под новую мажорную версию |
| Документация по версиям | Storybook для каждой мажорной версии |

## Чек-лист перед выпуском

- [ ] `npm run check` зелёный
- [ ] есть changeset с понятным текстом для пользователя (что изменилось и что ему делать)
- [ ] тип версии соответствует изменению (см. таблицу в главе 04)
- [ ] новые компоненты и пропсы экспортированы из `src/index.ts` — вместе с типами
- [ ] есть история в Storybook и тест, включая проверку axe
- [ ] проверено с клавиатуры и в тёмной теме

## Ошибки

> **Убрали экспорт или пропс в минорной версии.** Для SemVer это ломающее изменение — мажор
> (пока версия `0.x` — минор, и об этом честно пишут в журнале).
>
> **Публикация с локальной машины «как получится».** Без `prepublishOnly` в npm уходит
> непроверенная сборка. Здесь `prepublishOnly` запускает `npm run check`.
>
> **Журнал изменений пишется в день выпуска по памяти.** Changesets — запись в момент изменения.
>
> **Токен npm в репозитории или в секретах навсегда.** Публикация из GitHub Actions по доверенной
> публикации (OIDC) обходится без долгоживущего токена.
